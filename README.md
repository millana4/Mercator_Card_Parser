# Mercator Card Parser

Сервис парсинга карточек маркетплейсов. Умеет подбирать карточки под страту, например: Рубашки женские, 4 шт. 
А также умеет парсить данные карточек: на вход принимает URL или артикул, на выход отдает
сырой JSON `__NUXT__` или очищенные данные карточки согласно модели данных.

Сейчас поддерживает только Ozon.

Работать с сервисом можно двумя способами: синхронно через HTTP (Swagger) или
асинхронно через Redis — для интеграции с таск-менеджером.

## Стек технологий

- **Python 3.13**
- **FastAPI** — HTTP-API - Swagger на `/docs`
- **Selenium + selenium-stealth** — управляемый браузер с обходом антибота
- **Google Chrome (headless) + Xvfb** — рендеринг страниц Ozon
- **Pydantic / pydantic-settings** — модели данных и настройки
- **redis** — асинхронный транспорт задач (общий пул через списки)
- **Docker + Docker Compose** — упаковка и запуск (HTTP-сервис + воркер)
- **pytest** — тесты маппера, подбора и воркера

## Запуск в Docker

```bash
docker compose up --build
```
Swagger: http://localhost:8010/docs

## Эндпоинты Ozon
1. `POST /api/v1/ozon/card/by-url` — очищенная карточка по URL
2. `POST /api/v1/ozon/card/by-id` — очищенная карточка по артикулу
3. `POST /api/v1/ozon/select` — подбор карточек под страту
4. `POST /api/v1/ozon/category/by-url` — информация о категории по URL
5. `POST /api/v1/ozon/category/by-id` — информация о категории по ID
6. `POST /api/v1/ozon/raw/by-url` — сырой `__NUXT__` по URL
7. `POST /api/v1/ozon/raw/by-id` — сырой `__NUXT__` по артикулу
8. `POST /api/v1/ozon/search/diagnostics` — диагностика поисковой выдачи (служебный)


Файлы debug и служебные эндпоинты:
- `GET /api/v1/files`
- `GET /api/v1/files/{name}`
- `GET /api/v1/health`
- `GET /api/v1/health/ready`

Машиночитаемый контракт API: `http://localhost:8010/openapi.json`

Воркер запускается отдельным контейнером тем же образом (нужен тот же Selenium +
Chrome + Xvfb), отличается только команда — `python -m app.worker.run_worker`.
Он и HTTP-сервис независимы: можно поднять оба или любой по отдельности.

## Подбор карточек Ozon
На вход — параметры страты: 
- `query` - поисковый запрос, 
- `count` - требуемое количество карточек,
- `is_seasonal` - есть ли сезонное разделение, 
- `base_share` - доля базовых для сезонных предметов,
- `exclude` - уже отобранные карточки - исключения. 

На выход — распарсенные карточки.

## Работа через Redis

Кроме HTTP, сервис умеет работать как **консьюмер задач**: читает задачи из
Redis, выполняет их существующей логикой (подбор `select`, обход карточки
`parse`) и пишет результаты в списки результатов. Логика парсинга и подбора не
меняется — Redis это просто другой транспорт вместо HTTP.

Воркер тянет задачи из **общего пула** блокирующим `BRPOP` по ключам задач
своего региона (сначала подбор, затем обход), выполняет и кладёт результат
`LPUSH` в список результатов. Общий пул = work-stealing: любой свободный воркер
берёт следующую задачу; воркер, ушедший в антибот-cooldown, просто не тянет
новую — остальные продолжают разбирать очередь. Партиций, consumer-групп и
ручных коммитов нет (в отличие от прежней Kafka-схемы).

Запуск воркера (отдельный процесс, независим от HTTP):
```bash
python -m app.worker.run_worker
```

Ключи списков именуются `<поток>:<tasks|results>:<код региона>` (сейчас `spb`):

| Поток   | Список задач (читает)  | Список результатов (пишет) |
|---------|------------------------|-----------------------------|
| Подбор  | `select:tasks:spb`     | `select:results:spb`        |
| Обход   | `parse:tasks:spb`      | `parse:results:spb`         |

Маршрутизация по региону — через код гео в ключе (`OZON_GEO_CODE`): воркер региона
читает только свои ключи. Новый регион = воркер с другим `OZON_GEO_CODE`; списки
возникают сами при первой записи.

Сообщения — UTF-8 JSON в snake_case. Каждая задача несёт эхо-поля трассировки
(`task_id`, `set_id`, `stratum_id`, `card_id`, `geo`), которые воркер возвращает
в результате без изменений. Результат обхода дополнительно несёт `parser_id` —
какой воркер его отдал. На каждую задачу — ровно один результат; при сбое
возвращается `ok: false` с текстом в `error`.

Воркер отказоустойчив к Redis: если Redis недоступен при старте или упал в
процессе — воркер ждёт и переподключается, не падая. Обрабатывает задачи по
одной (Selenium не потокобезопасен); для параллелизма поднимается несколько
инстансов с разными `PARSER_ID`.

Надёжность: `BRPOP` удаляет задачу из списка сразу. Если воркер взял задачу и не
смог вернуть результат (упал, потерял сеть), задача не перечитывается воркером —
её переотправит ядро по истечении своего окна ожидания (`inflight-timeout`). Для
обхода это приемлемо (карточку обойдут снова), для подбора — редкий случай,
покрываемый автодобором.

## Наблюдаемость

Вместо consumer-групп Kafka:

- **`parser_id`** — идентификатор воркера (`PARSER_ID` в `.env`), проставляется в
  каждый результат; ядро логирует, кто ответил.
- **Счётчики в Redis** — воркер инкрементит `parser:<id>:done` на каждый
  успешный/неантиботный результат и `parser:<id>:antibot` на блокировку. Сводка:
  `redis-cli MGET parser:1:done parser:2:done parser:3:done`.
- **Длина очередей** — `redis-cli LLEN parse:tasks:spb` (сколько задач ждёт).

## Реакция на антибот

Воркер считает блокировки подряд. При серии (`OZON_ANTIBOT_STREAK_THRESHOLD`)
уходит в cooldown (`OZON_ANTIBOT_COOLDOWN_S`): закрывает браузер-сессию и на время
остывания IP перестаёт тянуть задачи. 
## Тесты
```bash
python -m pytest tests/ -v
```
Тесты гоняют маппер, логику подбора и обработчики воркера на сохранённом HTML из
`tests/fixtures/` — без обращения к Ozon (заход в карточку в тестах подбора
замокан). Меняя логику извлечения, отсева или расчёта потребности, сразу видно,
не сломалось ли что-то.

## Debug-файлы
При `DEBUG=true` каждый запрос сохраняет в `app/debug/`: полный HTML, сырой
JSON, JSON карточки и скриншот. Имя — `ozon_<sku>_<ГГГГММДД_ЧЧММСС>`; для страниц
выдачи — `search_<ГГГГММДД_ЧЧММСС>`.
В проде ставьте `DEBUG=false` — файлы не пишутся, файловые эндпоинты пусты.

Очистить:
```bash
sudo rm -rf app/debug/*    # если файлы созданы из контейнера root
```

## Настройки (.env)
Скопируйте `.env.example` в `.env`. Ключевое:

| Переменная | Назначение                                                           |
|---|----------------------------------------------------------------------|
| `DEBUG` | сохранять ли html/json/png и отдавать файловые эндпоинты             |
| `LOG_LEVEL` | DEBUG / INFO / WARNING / ERROR                                       |
| `OZON_RETRIES`, `OZON_*_TIMEOUT`, `OZON_PAUSE_*`, `OZON_RETRY_PAUSE_*` | политика Ozon: таймауты, паузы, ретраи (у каждого маркетплейса своя) |
| `OZON_MIN_RATING`, `OZON_MIN_REVIEWS` | пороги отсева кандидатов в подборе (рейтинг ≥, отзывов >)            |
| `OZON_MAX_PAGES` | потолок числа страниц выдачи при подборе                             |
| `REDIS_HOST`, `REDIS_PORT`, `REDIS_DB` | адрес Redis (IP:порт машины с Redis) |
| `REDIS_BRPOP_TIMEOUT_S` | таймаут блокирующего BRPOP, сек (потом воркер проверяет остановку) |
| `REDIS_RECONNECT_DELAY_S` | пауза между попытками переподключения к Redis, сек |
| `OZON_GEO_CODE` | код региона — суффикс ключей списков (напр. `spb`) |
| `OZON_GEO_NAME` | имя региона — эхо-поле `geo` в результатах |
| `PARSER_ROLE` | роль воркера: `primary` (обычный темп) или `reserve` (щадящий) |
| `PARSER_ID` | идентификатор воркера для наблюдаемости (1, 2, 3, …) |
